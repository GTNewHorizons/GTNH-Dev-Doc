---
title: Test cross-repository changes
description: Publish a modified GTNH mod locally and use that version from a dependent mod.
sidebar:
  order: 4
---

import { Steps, TabItem, Tabs } from '@astrojs/starlight/components';

Use this when one mod must build against an unpublished change from another.
GTNHGradle's
[version module](https://github.com/GTNewHorizons/GTNHGradle/blob/master/src/main/java/com/gtnewhorizons/gtnhgradle/modules/GitVersionModule.java)
supports the temporary `VERSION` override used below.

<Steps>

1. **Publish the modified dependency locally.**

   Choose a temporary version, run `publishToMavenLocal` in the dependency mod,
   and use the same version in the dependent mod:

   <Tabs syncKey="operating-system">
     <TabItem label="Linux, macOS, or Git Bash">

   ```shell
   VERSION=99.99.99 ./gradlew publishToMavenLocal
   ```

     </TabItem>
     <TabItem label="Windows PowerShell">

   ```powershell
   $env:VERSION = '99.99.99'
   .\gradlew.bat publishToMavenLocal
   Remove-Item Env:VERSION
   ```

     </TabItem>
   </Tabs>

   :::caution[Check the published coordinates]
   GTNHGradle uses `ARTIFACT_ID` when set, otherwise the Gradle project name.
   That name defaults to the local folder name but can be set in the project's
   settings. Renaming a checkout can therefore change its artifact ID.
   `ARTIFACT_GROUP_ID` and `RELEASE_VERSION` can also override publication
   coordinates; check your environment before publishing. See the
   [publishing module](https://github.com/GTNewHorizons/GTNHGradle/blob/master/src/main/java/com/gtnewhorizons/gtnhgradle/modules/PublishingModule.java).
   :::

   **Expected result:** GTNHGradle reports the override and
   `publishToMavenLocal` succeeds. The
   [GTNHGradle version module](https://github.com/GTNewHorizons/GTNHGradle/blob/master/src/main/java/com/gtnewhorizons/gtnhgradle/modules/GitVersionModule.java)
   reads the uppercase `VERSION` environment variable.

   Inspect the new POM in `~/.m2/repository/GROUP/PATH/ARTIFACT/99.99.99/`
   (`$HOME/.m2/repository/` in PowerShell). Group dots become directory
   separators. Confirm its `groupId`, `artifactId`, and `version`, and that the
   jar with the classifier required by the consumer, often `dev`, exists.

2. **Enable Maven Local in the dependent mod.**

   Check `repositories.gradle` or `repositories.gradle.kts` first. Some repositories already declare it. If
   it is missing, add `mavenLocal()` to the existing `repositories` block:

   ```groovy
   repositories {
       mavenLocal()
   }
   ```

3. **Use the local version in the dependent mod.**

   In `dependencies.gradle` or `dependencies.gradle.kts`, preserve the existing group, artifact,
   configuration, and classifier. Set its version to `99.99.99`. Do not add a
   `resolutionStrategy.force` rule.

   If the POM has a different artifact ID, correct the producer's project name
   or temporary `ARTIFACT_ID` override and republish before continuing.

4. **Refresh and test the dependent mod.**

   Inspect the resolved dependency before running the build or client:

   ```console
   ./gradlew dependencyInsight --dependency GROUP:ARTIFACT --configuration runtimeClasspath
   ```

   Replace `GROUP:ARTIFACT` with the POM coordinates. Use the relevant resolvable
   configuration if the repository customizes its runtime classpath; inspect
   `compileClasspath` too when testing an API change. On Windows, use
   `.\gradlew.bat`.

   **Expected result:** the selected version is `99.99.99`, with no conflict
   selecting a different version. Confirm the modified behavior in the
   consumer's normal build or development run.

   Republish after each producer change. If reusing the same version, resolve
   again with `--refresh-dependencies`; use a new temporary version when you
   need to distinguish iterations. Restart the consumer so it loads the new jar.

5. **Replace temporary settings before submission.**

   Once an online pre-release exists, replace `99.99.99` with that version in
   the consumer. Remove a `mavenLocal()` entry added only for this test and any
   temporary publication overrides. Review `git diff`, then repeat dependency
   inspection and the build from a clean checkout without the local artifact.

</Steps>

:::caution[Local means local]
GitHub Actions cannot access artifacts from your machine. CI requires an online
pre-release. Ask a GTNH team member if you cannot publish one, and link the
producer and consumer pull requests so reviewers can follow their dependency.
:::
