---
title: Test a change in the full pack
description: Replace the relevant jars or pack files in an isolated GTNH build and compare behavior.
---

import { Steps } from '@astrojs/starlight/components';

Use an assembled GTNH pack when the change depends on other mods, recipes,
configuration, saved data, or startup order. Run the owning repository's
checks first, then use a separate pack instance to compare unchanged and
modified behavior.

## Prepare the baseline

<Steps>

1. Choose a build from
   [GTNH Daily Builds](https://github.com/GTNewHorizons/GTNH-Daily-Builds/releases)
   that does not already include the change, and record its release tag.
   Download the client ZIP ending in `mmcprism-java8.zip` or
   `mmcprism-java17-26.zip` for the runtime you need. The
   [daily workflow](https://github.com/GTNewHorizons/DreamAssemblerXXL/blob/master/.github/workflows/daily-modpack-build.yml)
   defines the current names.
2. In Prism Launcher, use **Add Instance → Import** for the ZIP. Give the
   instance a test name, select a compatible game Java runtime, and launch the
   unchanged pack. Use a disposable world or a copy when testing existing data.
3. For server behavior, download the server ZIP from the **same release and
   Java variant**. Extract it separately and follow its included startup
   instructions. The Java 8 package provides `startserver.sh` and
   `startserver.bat`; the modern package provides `startserver-java9.sh` and
   `startserver-java9.bat`. Accept the Minecraft EULA only if you agree.
   Wait for `Done` and confirm the baseline client can join.

</Steps>

Reproduce the original problem or record the starting behavior. Keep the
setup and actions for the comparison, then close the client and server
before changing their files.

## Install the intended artifacts

For mod code, build the owning checkout using its README or CI command.
With RetroFuturaGradle's standard tasks, the unclassified reobfuscated jar in
`build/libs/` is the runtime artifact; the `-dev` jar is for development
classpaths. Its [jar-task reference](https://github.com/GTNewHorizons/RetroFuturaGradle/blob/master/docs/mcp-forge.md)
describes that distinction. Check custom packaging at the owning repository.

Open the test instance's game directory in Prism. Move the packaged mod out
of the game directory and copy in the built runtime jar. Check both `mods/`
and `mods/1.7.10/`: Forge scans both, so keep only one version of the mod in
each client or server instance. Install client-only mods on the client, and
install common/server changes on the sides their dependencies require.

If another unpublished mod is required, first
[build against its intended API](/GTNH-Dev-Doc/testing/test-cross-repository-changes/),
then install the matching runtime artifacts together.

For pack data or resources, copy the changed files to their corresponding
instance paths. Keep the originals so you can reset the test. Record the
source commits, jar names, or changed pack-file paths.

## Compare and verify

<Steps>

1. Launch the modified pack and inspect the mod list or startup log for the
   loaded versions. If the displayed version cannot distinguish a local build,
   compare the installed jar's checksum with the built artifact.
2. Repeat the baseline's setup and actions. For server state, use the matching
   dedicated server and observe the result from its connected client.
3. Exercise affected restart, save/reload, optional-dependency, and
   existing-world cases from
   [Testing expectations](/GTNH-Dev-Doc/testing/testing-expectations/).
   Use [in-game inspection](/GTNH-Dev-Doc/testing/in-game-testing-tools-and-tricks/)
   for recipe, item, and saved-data evidence.

</Steps>

Report the pack tag, runtime variant, installed artifacts, setup, and the
baseline and modified results. Say which important cases you didn't test.
If the test fails, keep the first useful exception using
[Locate logs](/GTNH-Dev-Doc/troubleshooting/locate-logs-and-useful-errors/).

Restore the original files or discard the instance before another unrelated
test.
